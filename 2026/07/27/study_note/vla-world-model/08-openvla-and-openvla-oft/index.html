OpenVLA 与 OpenVLA-OFT：VLA 不等于离散动作 Token

上一篇：RT-1 到 RT-2 ｜ 下一篇：π₀ 与 Flow Matching

1. 这篇文章解决什么问题？

OpenVLA 提供开放的 VLA 基线，便于研究数据转换、微调和跨任务评估；OpenVLA-OFT 则聚焦把 VLA 动作接口改造成更适于高效、连续控制的配方。

2. 前置知识

需要了解 VLM token 接口、动作量化和 LoRA；见 06 与 07。

3. 从腕相机抓取开始

若离散 token 每次只能逐 token 输出一个细粒度动作，控制频率和精度会受限。OFT 使用连续动作头、action chunk 和并行解码，把“理解指令”的骨干与“精确输出轨迹”的模块明确分工。

4. 核心概念

OpenVLA 基于 Prismatic VLM，组合视觉编码器（包括 SigLIP、DINOv2 组件）与 Llama 系列语言主干，在 Open X-Embodiment 数据上训练动作输出。OFT 的核心是连续动作头，可选 L1 回归或 diffusion，并行预测 chunk；FiLM 可用本体状态等条件调制视觉特征。它不是宣称原模型无效，而是针对动作解码延迟和量化误差的工程改造。

4.1 同一条 episode 适配 OFT 时要检查什么？

以 H=8, Da=7 为例，连续动作头一次输出 [B,8,7]；这 56 个浮点数不需要逐 token 自回归生成。若相机 key 从 front,wrist 改为 wrist,front，shape 仍完全正确，但视觉语义已被交换，因此适配器必须把相机顺序、状态字段、action frame 和归一化统计写进可版本化的配置。

4.2 “开放权重”不等于“换个机器人就能直接跑”

开放 VLA 的价值是让人能够检查模型、处理器、数据转换和微调接口；但 checkpoint 不会替你解决机器人之间的动作语义差异。至少有四层迁移要逐一回答：

层 源系统与目标系统可能不同的地方 若忽略会怎样
相机 相机数量、安装位姿、内参、裁剪 模型将腕相机当前视，或看见未见过的视角
本体状态 关节数、顺序、夹爪编码、力传感器 状态 token 没有物理对应
动作 关节/末端、base/world frame、控制频率 输出方向或幅值错误
任务语言 prompt 模板、物体命名、成功定义 语言条件被弱化或误解

例如源数据使用“夹爪开度 0 表示闭合，1 表示张开”，而目标设备恰好反过来；即便视觉和语言全对，策略也会在最关键的抓取时做反动作。最稳妥的迁移起点，是先用目标机器人采一小批可验证的示教，让动作头和归一化统计对齐，再讨论更大规模微调。

4.3 LoRA 在 VLA 微调中实际改了什么

对一个原始权重矩阵 (W\in\mathbb R^{d_{out}\times d_{in}})，LoRA 不直接更新完整 (W)，而是学习低秩增量：

[
W’=W+\alpha BA,\qquad
A\in\mathbb R^{r\times d_{in}},\ B\in\mathbb R^{d_{out}\times r}
]

当秩 (r) 很小，训练参数和显存占用会下降。直觉上，底座 VLM 保留通用的视觉语言能力，adapter 学“本实验室任务、相机和指令措辞的偏移”。

但 LoRA 不是数据质量的替代品：

  • adapter 只能在它挂载的底座版本、tokenizer、视觉处理器上解释；
  • 若动作头是新初始化的，少量 LoRA 参数不会凭空让它学会安全控制；
  • 若微调集只含一个桌面、一个光照，adapter 可能过拟合背景；
  • checkpoint 发布时应一并保存 base model ID、adapter 配置、action spec、normalization ID 和 prompt 模板。

4.4 连续动作专家怎样和 VLM 特征连接

可将 VLM 输出看作长度为 (N) 的 token 序列 (F\in\mathbb R^{B\times N\times D})。动作专家不一定要把全部 token 平均掉；它可通过交叉注意力查询与当前动作有关的信息：

[
Q_{action}=\text{LearnedQueries},\quad
Z=\text{CrossAttention}(Q_{action},F),\quad
\hat A=h(Z,s_t)
]

若有 H 个查询，每个查询可对应 chunk 内的一个时间位置，最终输出形状为 ([B,H,D_a])。这说明“连续头”并不是在忽略语言或视觉，而是用另一种解码方式读取同一套多模态特征。

实践中应明确本体状态在何处注入：拼接到动作头、作为单独 token、还是用 FiLM 调制。三种方式都可行，但训练与部署必须保持同一种接口。

4.5 优化实时性时先做 deadline，而不是只看平均耗时

控制系统最危险的不是偶尔慢 2 ms，而是偶发 300 ms 卡顿后执行一个已过期的 chunk。给每段预测写入生成时间和有效期：

6. 训练过程

先将数据转为目标模型所需 schema，验证图像、语言、state、action 的对齐；冻结部分骨干并 LoRA 微调时，动作头仍需足够的任务数据。不要把不同机器人 action spec 生硬混在一个损失里。

7. 推理和部署过程

连续头输出 [H,Da] 后执行 receding horizon；实际吞吐需要测“预处理+VLM+动作头+安全层”。官方 OFT 报告了相对其基线的加速与成功率结果，但它们是特定基准设置下的论文结果，不是所有机器人上的保证。

8. 公式解释

[\hat A_t=h_\psi(F_\theta(I,g),s_t)]

(F_\theta) 是 VLM 骨干，(h_\psi) 是连续动作头，(I,g,s_t) 分别是图像、指令和本体状态，输出 (\hat A_t\in\mathbb R^{H\times D_a})。该式展示 VLA 可有非 token 动作头。

8.1 端到端延迟要按时间线而不是模型前向算

即使动作头从 20 ms 优化到 2 ms，系统也不是“10 倍更实时”；应测 p50/p95 总延迟，并让 action buffer 丢弃过 deadline 的旧 chunk。

11. 常见误解

“VLA = 动作 token”是错误的。动作 token、L1 回归、扩散和 flow matching 都可作为从语义到控制的接口。
